# Plotly.js 代替チャートライブラリ 比較レポート

**対象**: ModbusSimpleLogger のチャート描画系 (`src/plotly.ts` / `src/components/ChartPanel.tsx`)
**目的**: 現状の Plotly.js より軽量で、WebGL 不可環境へフォールバックでき、
Android / iOS / Linux / Windows / macOS で動作するチャートシステムの列挙・比較
**性能根拠**: 代替ライブラリの数値は各プロジェクトの公表値・公式ドキュメント・文献のみで、**未実測**。
現行 Plotly のバンドルサイズのみ `bun run build` による**実測値**（§5-1）。
描画性能の実機確認手順は §11 に記載。

## 1. 調査中に覆った 3 つの想定

本レポートの結論は調査中に 3 回変わった。訂正の履歴自体が技術的な要点を含むため記録する。

### 訂正1: uPlot は内部でデータ間引きをしない

当初「uPlot は点数がピクセル幅を超えると 1px ごとの min/max に畳むので描画コストが飽和する」と
想定したが、**逆**だった。uPlot の公式方針は
「パース・集約・統計処理はライブラリ内で行わない、事前に済ませること」であり、
最適化が効くのは *点数 ≤ ピクセル幅* のとき。32768 点なら 32768 セグメントを実際に描く。
**間引きはアプリ側の責務**である。

### 訂正2: Canvas2D は「常に GPU」ではない

Chromium の Canvas2D 自体は GPU アクセラレーション対象だが、Skia は
**アンチエイリアス付きの凹パス**（長い折れ線がまさにこれ）を GPU でラスタライズできず、
CPU ラスタライズ → テクスチャ転送に落ちる。
一方 WebGL は float 配列を直接渡せ、GPU は line segment / triangle strip の描画そのものが得意。

→ **多点折れ線において WebGL に構造的な優位があるのは事実**であり、
「1024 点程度なら Canvas2D で十分」という主張は、その点数規模でのみ成立する条件付きの結論だった。

### 訂正3【最重要】: XY パラメトリック曲線が候補の大半を失格させる

本アプリの X 軸候補は **49 種**（`time` + `raw_00..15` + `phy_00..15` + `par_00..15`、
`src/App.tsx:191-207` / `AI_CHANNELS = PARAM_CHANNELS = 16`）。
用途にはひずみ-応力の**繰り返しヒステリシスループ**が含まれる。これは y = f(x) の関数ではなく
**パラメトリック曲線 (x(t), y(t))** である。

- 同じ x に往路と復路で**異なる y** が乗る（x は一意でも昇順でもない）
- **ループが囲む面積そのものが計測対象**（散逸エネルギー）なので形状を壊せない
- サイクル間のドリフト／ラチェッティングを見たいので、周回を重ね書きで潰してはいけない

この一点が、以降のすべての評価を支配する。

## 2. 【足切り】パラメトリック描画モデルの有無

**性能比較より先にこの表を読むこと。** ここで失格した候補は、どれだけ軽量でも採用できない。

| ライブラリ | x 昇順ソート要求 | XY ループ描画 | 判定 |
|---|---|---|---|
| **uPlot** | **要求**（x は数値・一意・昇順） | **不可** | ❌ **失格** |
| **dygraphs** | 要求（時系列前提） | 不可 | ❌ **失格** |
| **TradingView Lightweight Charts** | 要求（X 軸が時刻専用） | 不可 | ❌ **失格** |
| **TimeChart** | 要求（大規模時系列特化） | 不可 | ❌ **失格** |
| **Chart.js 4** | 不要（scatter + `showLine: true`、`{x,y}` を配列順に結線） | 可 | ✅ 通過 |
| **Apache ECharts 5** | 不要（line series に `[[x,y],...]` を配列順で）※要検証 | 可 | ✅ 通過 |
| **webgl-plot** | 不要（頂点バッファを配列順に描画） | 可 | ✅ 通過 |
| **Plotly `scattergl`**（現状） | 不要 | 可 | ✅ 通過（基準線） |
| ApexCharts / Observable Plot / D3 | 不要 | 可 | △ 規模で脱落（§6） |
| Highcharts / LightningChart JS / SciChart JS | 不要 | 可 | △ 商用ライセンスで脱落（§6） |

> **本レポートで最も価値のある結論**:
> 「軽量チャートライブラリ」の上位を占める uPlot・Lightweight Charts・dygraphs は
> **いずれも時系列 (y = f(t)) を前提としたデータモデル**を持つ。
> これらは本アプリの XY モードで**原理的に使用できず、回避策も存在しない**。
> サイズ表だけを見て選定すると必ず誤る。

**補足**: モード A（時系列）**専用**としてなら uPlot は依然として最有力である。
「時系列は uPlot / XY は別ライブラリ」の 2 本立ても選択肢として §7 に記載する。

## 3. 現状の設計判断の再確認 — なぜ `scattergl` だったのか

`src/components/ChartPanel.tsx:189-190`:

```ts
type: 'scattergl' as const,
mode: 'lines' as const,
```

この選択は **性能のためだけでなく、データモデルとして必然**だった。

- Plotly の **scatter トレースは点列を配列順に結線する**パラメトリック曲線モデルであり、
  x の単調性・一意性を要求しない。
- 一方、多くのライブラリの「line チャート」は y = f(x) を前提とし x 昇順ソートを要求する。
- → **ヒステリシスループを描ける系統が scatter 系のみ**であり、現状の採用は正しい。

**したがって Plotly を置き換えるなら、scatter 相当のパラメトリック描画モデルを持つものに限る。**
これが移行判断の第一原則である。

> なお `AGENTS.md` の従来の記述は「フル `plotly.js` を import 禁止（バンドル肥大のため）」という
> **サイズの話しか書いておらず**、この必然性が記録されていなかった。
> そのため「もっと軽い line チャートに替えればよい」という誤った推論を誘発しやすい状態だった。
> 本レポートと同時に `AGENTS.md` を更新済み。

## 3.5. 【重要】Plotly を捨てる前に — 未使用設定と踏んでいる既知バグ

> ✅ **本節の内容は v3.1 で実装済み。** 変更点のまとめは §3.6 を参照。

「Plotly でも間引きながら軽量に GPU プロットできるはず」という指摘は**正しい**。
そして調査の結果、**現行実装は Plotly の性能を引き出しきれておらず、
かつ既知バグの回避策が逆効果になっている疑いが強い**ことが判明した。

**ライブラリを替える前に、まずここを潰すべきである。**

### 3.5-1. 踏んでいる可能性が高い既知バグ

#### (A) `Plotly.purge()` は WebGL コンテキストを破棄しない

`ChartPanel.tsx:295` の `key={purgeEpoch}` による強制 remount は、
コミット `98bd676`「scattergl は多数の更新で GPU 側の状態を蓄積する」への対策として入っている。
react-plotly.js はアンマウント時に `Plotly.purge()` を呼ぶ。

しかし **plotly.js の既知の問題として、`Plotly.purge()` は scattergl (regl) の
WebGL コンテキストを破棄しない**（[issue #2852](https://github.com/plotly/plotly.js/issues/2852)、
[issue #6365](https://github.com/plotly/plotly.js/issues/6365) — **#6365 は現在も open / P3 backlog**）。

> issue #6365 報告者:
> 「単一のプロットコンポーネントのデータが変わったとき、以前の WebGL コンテキストは生き残り、
> 最終的にプロットを多数持っているのと同じ結果になる」

つまり **remount するたびに新しいコンテキストが生成され、古いコンテキストは解放されない**可能性が高い。

- 15 分ごとの定期パージ × 4 チャート = **15 分ごとに 4 コンテキストずつ増加**
- 加えて再間引き時 (`App.tsx:459-462`) にも `setChartEpoch` で remount が走る
- ブラウザのコンテキスト上限（概ね 8〜16）に対し、**1 時間以内に上限へ到達する計算**

上限に達すると `Too many active WebGL contexts. Oldest context will be lost.` が出て
**古いチャートが黙って描画を止める**。

> **つまり `purgeEpoch` による remount は、GPU 状態の累積を抑えるどころか、
> コンテキストリークを毎回増やしている可能性がある。**
>
> ⚠️ **要検証**: 本リポジトリの plotly.js は **3.7.0** であり、上記 issue の報告時点より新しい。
> 3.x で修正済みの可能性は否定できない。§3.5-3 の手順で実機確認すること。
> ただし #6365 が open のままである以上、**修正済みと仮定するのは危険**である。

#### (B) 対策: `WEBGL_lose_context` による明示的な解放

コミュニティで確立している回避策は、アンマウント直前に自分でコンテキストを殺すこと:

```ts
const canvas = graphDiv.querySelector('canvas') as HTMLCanvasElement | null;
const gl = canvas?.getContext('webgl2') ?? canvas?.getContext('webgl');
gl?.getExtension('WEBGL_lose_context')?.loseContext();
```

`purgeEpoch` remount の直前にこれを挟めば、既存の設計を保ったままリークを止められる。
**これが本レポートで最も費用対効果の高い改善提案である。**

#### (C) 4 チャート分のコンテキストを 1 つに多重化する

[issue #2333](https://github.com/plotly/plotly.js/issues/2333) の通り、Plotly は複数 graph div 間で
WebGL コンテキストを共有しない。Plotly 公式が案内する回避策は
**virtual-webgl** スクリプトによるコンテキスト多重化である。

- 既知の副作用として「virtual-webgl は 3D / surface / mesh3d の描画を壊す」
  （[issue #7298](https://github.com/plotly/plotly.js/issues/7298)）が報告されているが、
  **本アプリは 2D の scattergl しか使っていないため、この副作用は該当しない。**
- 4 コンテキスト → 1 コンテキストになり、iOS WKWebView のコンテキスト上限リスク（§8）も同時に軽減する。

### 3.5-2. 使っていない性能設定

現行の trace / config（`ChartPanel.tsx:184-240`）で**指定されていない**もののうち、
効果が見込めるもの:

| 設定 | 現状 | 効果 | 注意点 |
|---|---|---|---|
| **`hoverinfo: 'skip'`**（trace） | 未指定（= hover 有効） | **最大の改善候補**。scattergl はホバー判定用の空間インデックスを毎更新で構築する。`'skip'` はラベルとイベントの両方を止め、この構築を回避する | **ホバーで値を読む機能が失われる**。`'none'` ならラベルのみ抑止しイベントは残る。UX とのトレードオフ |
| **`hovermode: false`**（layout） | 未指定 | 上記と併用。ただし**ラベルは消えるがホバー時の線は残る**（[issue #1987](https://github.com/plotly/plotly.js/issues/1987)） | 単独では不十分。`hoverinfo` と併用すること |
| **`plotGlPixelRatio`**（config） | 未指定（既定 2） | HiDPI / Android でフラグメント処理量を削減 | ⚠️ **[issue #5497](https://github.com/plotly/plotly.js/issues/5497)「plotGlPixelRatio has no effect on scattergl」** — scattergl では効かない可能性がある。**期待しないこと** |
| **`Plotly.extendTraces`** | 未使用（毎回 `Plotly.react` 相当の全再描画） | 追記のみのモード A では大幅に安い | 間引き・再間引きでバッファが作り直されるため、本アプリの構造では適用範囲が限定的 |
| **`Float32Array`** | `Float64Array` を使用（`ChartPanel.tsx:161-162`） | regl は最終的に Float32 へ落とすため、メモリとコピーが半減 | ⚠️ **時刻軸には使用不可**。epoch-ms（約 1.7×10¹²）は Float32 の 24bit 仮数に収まらず、**分解能が約 10⁵ ms（≒100 秒）まで劣化する**。Y 軸や物理値軸のみ安全 |

> **`hoverinfo: 'skip'` が効くのは、本アプリがカスタム hover テンプレートも
> `onHover` イベントも使っていないため**（`ChartPanel.tsx` にイベントハンドラなし）。
> 既定のホバー表示を UX として残したい場合は、この最適化は使えない。
> 「8192 点以上でホバー付き scattergl は重くなる」というのはコミュニティで広く報告されている。

### 3.5-3. Plotly 側の間引きについて

**Plotly.js には組み込みの間引き機能は無い**（Plotly.py にも無い）。
間引きはアプリ側の責務であり、本アプリは既に `App.tsx:436-463` で stride 間引きを実装している。

したがって「Plotly で間引きながら GPU プロットする」構成は**既に成立している**。
残る課題は 2 つだけ:

1. stride 間引きがスパイクを落とす（§4-1）→ **min/max 間引きへの置換で解決**
2. WebGL コンテキストのリークと未使用の性能設定（本節）→ **設定追加と `WEBGL_lose_context` で解決**

### 3.5-4. 検証手順（実施推奨）

コンテキストリークの有無は簡単に確認できる:

1. アプリを起動し 4 チャートを表示、DevTools コンソールを開く
2. `CHART_PURGE_INTERVAL_MS` を一時的に 15 分 → 10 秒に変更して remount を強制的に頻発させる
3. コンソールに `Too many active WebGL contexts. Oldest context will be lost.` が出るか観察
4. 出る場合 → **リークが実在**。§3.5-1(B) の `WEBGL_lose_context` 解放を入れて再測定
5. 出ない場合 → plotly 3.7.0 で修正済み。`purgeEpoch` 戦略はそのままでよい

## 3.6. v3.1 で実施した Plotly 最適化

§3.5 の調査結果にもとづき、**ライブラリを替えずに** 以下を実装した。

### 変更点

| # | 変更 | ファイル | 根拠 |
|---|---|---|---|
| 1 | trace に **`hoverinfo: 'skip'`** を追加 | `ChartPanel.tsx` | scattergl のホバー用空間インデックス構築を毎更新で回避 |
| 2 | layout に **`hovermode: false`** を追加 | `ChartPanel.tsx` | mousemove 時のヒットテスト自体を停止（単独では不十分なため 1 と併用） |
| 3 | **`releaseWebglContext()`** を追加し、チャート差し替え時と panel アンマウント時に `WEBGL_lose_context` でコンテキストを明示解放 | `ChartPanel.tsx` | `Plotly.purge()` がコンテキストを破棄しない問題（#2852 / #6365）への対処 |
| 4 | **定期パージ (`CHART_PURGE_INTERVAL_MS` = 15分) を廃止** | `constants.ts` / `App.tsx` | 3 により不要になり、かつリークを増やす側に働いていたため |
| 5 | **`CHART_MAX_POINTS` を 1024 → 2048** | `constants.ts` | 1・2 で確保した予算を点数に振り向け |
| 6 | アプリバージョン **3.0 → 3.1** | `package.json` | — |

### 定期パージを廃止した理由

定期パージは「scattergl の GPU 状態累積を抑える」目的だったが、
`Plotly.purge()` がコンテキストを解放しない以上、
**15 分ごとに 4 チャート分の新規コンテキストを確保しつつ古い方を捨てられない**動作になる。
ブラウザのコンテキスト上限（概ね 8〜16）に対し、これは累積を抑えるどころか加速させる。

変更 3 でコンテキストを明示解放するようにしたため、
定期パージが担っていた役割は根本的に解消された。
なお**保存パスの再間引き時の remount は残している** — これは定期的なタイマーではなく、
点数が半減する実際の視覚的不連続点であり、その瞬間に作り直すのは妥当だからである。

### `hoverinfo: 'skip'` のトレードオフ（要確認）

⚠️ **これはユーザー体験の変更を伴う。**
`'skip'` はホバーラベルとホバー/クリックイベントの**両方**を止めるため、
**グラフ上にカーソルを乗せて数値を読む操作ができなくなる**。

- 本アプリは `hovertemplate` も `onHover` / `onClick` ハンドラも使っていないため、
  内部的に壊れるものは無い（インデックス構築が純粋な無駄だった）。
- しかし**利用者がホバーで値を読んでいた場合、それは失われる**。
- 復活させる場合は `hoverinfo` の行を削除するだけでよい（1 行）。
  ただしその場合、点数を 2048 に上げた分のコストが戻るため、
  `CHART_MAX_POINTS` を 1024 に戻すことも併せて検討すること。

### 採用しなかったもの

| 項目 | 不採用の理由 |
|---|---|
| **`plotGlPixelRatio`** | [issue #5497](https://github.com/plotly/plotly.js/issues/5497)「plotGlPixelRatio has no effect on scattergl」により、scattergl では効かない可能性が高い。効果が不確実な設定を入れても判断を濁らせるだけ |
| **`Float32Array` 化** | 時刻軸で使えない（epoch-ms が Float32 の 24bit 仮数に収まらず分解能が約 100 秒に劣化）。軸ごとに型を出し分ける複雑さに見合わない |
| **`Plotly.extendTraces`** | 間引き・再間引きでバッファが作り直されるため、追記専用の最適化が効く場面が限られる |
| **virtual-webgl** | 4 コンテキスト → 1 に多重化できるが、外部スクリプトの追加はオフライン PWA の資産管理を複雑にする。まず 3・4 の効果を実機で確認してから判断すべき |

### 未実施（今後の候補）

- **min/max 間引きへの置換**（§4-1）— stride 間引きのスパイク欠落は未解決
- **virtual-webgl によるコンテキスト多重化**（§3.5-1(C)）
- **8192 点以上への引き上げ** — 2048 は今回の最適化で確実に賄える範囲に留めた保守的な値。
  §11 の実機確認を経てから更に上げること

## 4. 2 つの描画モードと間引き戦略

`ChartPanel.tsx:209` で 1 つのコンポーネントが両モードを担う:

```ts
type: xAxis === 'time' ? ('date' as const) : ('linear' as const),
```

- **モード A: 時系列**（X = time、x 単調増加）
- **モード B: XY パラメトリック**（X = 任意チャネル、ヒステリシスループ等、x 非単調・非一意）

### 4-1. モード A: min/max ピクセル間引きが有効

1px 区間ごとに**最小値と最大値の 2 点だけ**残す方式。

- 描画コストが **O(点数) → O(ピクセル幅)**。幅 800px なら約 1,600 点に固定され、
  32768 点でも 1M 点でも描画コストは変わらない。
- 視覚的に等価（1px 幅の縦線として描かれる範囲が元データと一致）。
- dygraphs / Grafana / Highcharts Boost が採用する定石。

**現行の stride 間引きの問題** (`src/App.tsx:436-463`):

```ts
for (const p of pointsToAdd) {
  if (saveRawCounterRef.current % saveDecimationStrideRef.current === 0) {
    buffer.push(p);
  }
  saveRawCounterRef.current++;
}
if (buffer.length > 2 * CHART_MAX_POINTS) {
  const decimated: DataPoint[] = [];
  for (let i = 0; i < buffer.length; i += 2) decimated.push(buffer[i]);
  dataBufferRef.current = decimated;
  saveDecimationStrideRef.current *= 2;
  ...
}
```

2 点に 1 点を**無条件に捨てる**ため、単サンプル幅の尖頭値が消える。
HX711 ロードセル / ADS1115 の計測器としてこれは実害であり、
min/max 間引きは軽量化だけでなく**計測の正しさとして上位互換**である。

> なお全点は TSV へ記録されるため、失われるのは画面表示のみ。
> ただし「画面で見えなかったスパイクは気づかれない」ため、実用上の意味は小さくない。

### 4-2. モード B: min/max は使用不可

列ごとの min/max は「1 つの x に 1 つの y 範囲」を仮定するため、
往路と復路を 1 本に潰して**ループを破壊する**。代替手法:

| 手法 | 特性 | 削減率 |
|---|---|---|
| **連続ピクセルセル重複除去** | 直前に採用した点と同じピクセルセルに落ちる点を捨てる。軌跡の形状と**周回ごとのドリフトを保存**する（グローバル重複除去は周回情報を消すため**不可**） | 軌跡のピクセル長 × 周回数に依存。保証なし |
| **RDP (Ramer-Douglas-Peucker)** | 形状誤差を閾値以下に保ちつつ 2D 折れ線を簡略化 | 曲率に依存。計算コスト高 |

いずれも**削減率が保証されない**。したがってモード B では
「間引きで解決」ではなく「**全点を高速に描く**」設計が必要になる。

> **WebGL の必要性はモード B から来る。**
> モード A だけを見て「間引けば Canvas2D で十分」と判断すると、実負荷を過小評価する。

### 4-3. 点密度の目安（モード A のみ成立）

チャート幅 800px の場合:

| 点数 | 1px あたり | モード A | モード B |
|---|---|---|---|
| 1,024 | 約 1.3 | 間引き不要 | 間引き不要 |
| 8,192 | 約 10 | min/max で約 1,600 点へ | 削減率は軌跡次第 |
| 32,768 | 約 41 | min/max で約 1,600 点へ | 削減率は軌跡次第 |

**モード B ではこの「1px あたり 41 点だから大半が冗長」という論法が成立しない。**
ヒステリシスループでは軌跡が同じピクセル領域を何度も通過するが、
それは冗長ではなく**周回ごとに意味のある別の情報**である。

### 4-4. 間引きを自前実装するメリット・デメリット（計算時間 vs 描画時間）

#### 結論を先に

> **min/max 間引きは「描画を速くする」施策ではない。「同じ点数でより正確にする」施策である。**
>
> 現在の点数予算（2048 点）では、min/max 間引きに置き換えても**描画時間はほぼ変わらない**。
> Plotly に渡る点数が 2048 → 約1,600（800px × 2）になるだけで、桁が動かないからである。
> 得られるのは**スパイクの保存**であり、失うのは**メモリと主スレッド時間**である。
>
> 「計算時間 vs 描画時間のトレードオフ」として成立するのは、
> **描画点数を今より大幅に増やしたい場合に限る**。

#### なぜ「今のままでは速くならない」のか — 現行アーキテクチャの制約

最も重要な事実: **現在 `dataBufferRef` には既に間引き済みの点しか入っていない。**

`App.tsx` の保存パスは、取り込み時点で stride 間引きしてからバッファに積む。
全点は TSV にのみ流れ、メモリには残らない（「保存時間によらずメモリと 1 フラッシュあたりのコストが一定」という設計）。

つまり **min/max 間引きを今のバッファに掛けても、スパイクは既に捨てられた後**であり、
何も復元できない。**fidelity を得るには、間引き前のデータを保持する必要がある**
— これが本質的なコストである。

#### 3 つの設計案とトレードオフ

| 案 | 保持データ | 取り込みコスト | 再描画コスト | メモリ | スパイク保存 | ズーム対応 |
|---|---|---|---|---|---|---|
| **現状 (stride)** | 約 2048 点 | O(1)/点 | O(1)（そのまま渡す） | 一定・最小 | ❌ 失う | 既に捨てた点は戻らない |
| **A: 全点保持 + 描画時 min/max** | 全点 | O(1)/点 | **O(N)** N=全点数 | **O(全点数)・無制限に増加** | ✅ 完全 | ✅ 任意区間を再計算可 |
| **B: インクリメンタル min/max** | 約 2×幅 | O(1)/点 | O(1) | 一定・最小 | ✅ 表示区間内 | ❌ ズーム時に再構築不可 |
| **C: 中間リザーバ（推奨）** | 表示幅の 8〜16 倍（約 16k 点） | O(1)/点 | O(M) M≈16k | **一定（上限あり）** | ✅ 1/8〜1/16 px 精度まで | △ リザーバ範囲内なら可 |

**案 A の計算量の実感**（20 Hz サンプリング、5 fps 再描画）:

| 計測時間 | 全点数 | 1 再描画あたりの走査 | 毎秒の走査量 | 評価 |
|---|---|---|---|---|
| 1 時間 | 72,000 | 72,000 | 36 万 | 余裕 |
| 8 時間 | 576,000 | 576,000 | 288 万 | まだ許容 |
| 24 時間 | 1,728,000 | 1,728,000 | 864 万 | **主スレッドが厳しい** |

メモリも問題になる。`DataPoint` は 48 値（AI raw 16 + AI phy 16 + param 16）を持つため、
`Float32Array` 換算で 1 点あたり約 192 バイト。24 時間で **約 330 MB** — Android では非現実的。

> **案 A は「計算時間 vs 描画時間」ではなく「メモリ vs 正確性」のトレードオフになる。**
> しかも増え方が計測時間に比例するため、長時間ロガーとしては破綻する。
> 現行の「stride 間引きでメモリ一定」という設計判断は、この点では合理的だった。

#### この app 固有の最大のリスク: 主スレッド占有が計測を乱す

これは一般的なチャート最適化の議論には出てこないが、**本アプリでは最も重要**である。

- 本アプリは**データロガー**であり、Modbus ポーリングは `setTimeout` 再帰で主スレッド上を回る。
- 間引き計算も主スレッドで走る。
- **間引きが重くなると、ポーリング周期にジッタが乗る。**
  描画が多少カクつくのは許容できても、**計測周期が乱れるのは計測データの品質を直接損なう。**

→ したがって:
1. **取り込み時 O(1) を維持すること**が最優先（案 B / C はこれを満たす、案 A も取り込みは O(1)）
2. 再描画時の O(N) 走査が数 ms を超えるなら **Web Worker へ移す**べき
   （本リポジトリは既に `tsvWriterWorker` / `pyodideWorker` で Worker を運用しており、素地はある）
3. 実機確認では**フレームタイムだけでなくポーリング周期のジッタも測る**こと

#### モード別に実装が二重化する問題

§4-2 の通り **min/max はモード B（XY ループ）では使用不可**。したがって:

- モード A: min/max 間引き
- モード B: 連続ピクセルセル重複除去 or RDP

**2 種類の間引きを実装し、軸の種類で切り替える**必要がある。
`ChartPanel` は 1 コンポーネントで両モードを担っているため、
間引きロジックをどこに置くか（`App.tsx` の取り込み側か、`ChartPanel` の描画側か）で
設計が変わる。**ズーム対応を考えると描画側に置く方が自然だが、
描画側は 4 チャート分走るため計算量が 4 倍になる。**

#### 推奨する進め方

**今すぐやるべきではない。** 理由は 3 つ:

1. v3.1 の最適化（§3.6）の効果がまだ実機で測れていない。
   ホバーインデックス除去だけで十分な余裕が出た可能性がある。
2. 現在の 2048 点では min/max にしても**描画は速くならない**（冒頭の結論）。
3. スパイク欠落が実運用で実害になっているかが未確認。
   HX711 / ADS1115 の実データでどの程度の尖頭値が失われているかを先に確認すべき。

**順序**:

1. **§11-1 の実機確認**（v3.1 の効果測定）
2. **スパイク欠落の実害確認** — 同一計測を TSV 全点と画面表示で比較し、
   見逃している尖頭値の大きさを把握する
3. 実害があるなら **案 C（中間リザーバ）** を実装。
   メモリ一定という現行の設計思想を壊さず、スパイク保存を得られる唯一の案である
4. 点数を 8192 以上に上げたい場合のみ、**Worker への移設**を検討

**案 C の概要**: 表示幅の 8〜16 倍（約 16k 点）の固定長リングバッファを持ち、
取り込み時に O(1) で min/max を更新する。描画時はここから表示幅ぶんへ落とす。
メモリは一定、取り込みは O(1)、スパイクは 1/8〜1/16 px 精度まで保存される。

## 8. プラットフォーム適合と WebGL 固有リスク

Canvas2D は Android / iOS / Linux / Windows / macOS の全モダンブラウザ・全 WebView
（Chromium / WKWebView）で例外なく利用可能。**差が出るのは WebGL 依存の候補のみ。**

### WebGL 固有リスク（4 チャート同時が効く）

1. **コンテキスト数上限**: ブラウザの WebGL コンテキスト上限は概ね 8〜16。
   本アプリは 4 個を常時消費する。**iOS WKWebView は特に厳しく**、コンテキストロストのリスクがある。
2. **ソフトウェアラスタライズへの転落**: Android 低価格帯 / GPU ブラックリスト端末、
   VM・リモートデスクトップ上の Linux / Windows では WebGL が SwiftShader に落ち、
   **Canvas2D より遅くなる**。
3. **GPU 状態の累積**: 本リポジトリは既にこの対処を実装済み — `constants.ts:33`
   `CHART_PURGE_INTERVAL_MS = 15 * 60_000` と `purgeEpoch` による強制 remount
   （`ChartPanel.tsx:295` の `key={purgeEpoch}`）。
   コミット `98bd676` のメッセージ通り「scattergl は多数の更新で GPU 側の状態を蓄積する」ため。
   **これは理論上のリスクではなく、実測済みの既存問題である。**

### `detectRenderBackend()` の表示について

`ChartPanel.tsx:46-71` は WebGL コンテキストが取得できない場合に
`{ api: 'Canvas2D', accel: 'CPU' }` を返すが、§1 の訂正 2 の通り
**Canvas2D は GPU に載る場合もある**ため、この表示は不正確。
逆に WebGL でも SwiftShader なら CPU である（こちらは正しく検出している）。

→ **「Canvas2D = CPU」「WebGL = GPU」の二分法はどちらの方向にも不正確**であり、
描画方式の性能判断はこの表示ではなく実機計測で行うこと。
なおこの関数は Plotly の DOM 構造（`graphDiv.querySelector('canvas')`）に依存しているため、
どの候補へ移行しても書き直しが必要。

## 9. 推奨（条件分岐）

単一解は存在しない。**モード B の点数目標と実装工数の許容度**で選択が変わる。

| シナリオ | 推奨 | 理由 |
|---|---|---|
| **移行工数を最小化したい** | **Plotly 現状維持** | 8192〜32768 点 × 4 枚は今日すでに動く。争点は「gzip 487KB（実測）を払う価値があるか」のみ。既知バグ側は v3.1 で解消済み |
| **8192 点 × 4 枚、両モード、単一ライブラリ** | **ECharts**（次点 Chart.js） | 足切り通過かつ Canvas/SVG 選択可。Plotly の約 1/5〜1/8 |
| **32768 点 × 4 枚、モード B も全点描画** | **二段構え: webgl-plot + ECharts/Chart.js** | 131,072 点/フレームは WebGL の領域。**軸描画の自前実装が最大の障壁** |
| **時系列と XY で実装を分けてよい** | **モード A: uPlot / モード B: ECharts** | 時系列側は uPlot が圧倒的（約 15KB）。`ChartPanel` 二重実装コストと引き換え |
| **保守体制を最優先** | **ECharts** | Apache 財団バックアップでバス係数が最も高い |

### 総合最有力: Apache ECharts

1. 足切り（R4b）を満たし、**両モードを 1 つのライブラリで賄える**
2. **Canvas / SVG を init 時に選べ**、要件の「WebGL 不可時のフォールバック」に最も近い
3. `large` / `progressive` による大規模データ対策を持つ
4. **Apache 財団 + 企業バックアップ**で保守体制が最も厚い
5. Plotly の約 1/5〜1/8（実測 gzip 487KB → 約 60〜100KB）

**リスク**:
- uPlot ほど軽くない（約 60〜100KB）
- `large` / `progressive` がモード B で効くかは**未検証**
- WebGL ではないため、**32768 点 × 4 枚が 200ms 予算に収まるかは実機確認が必須**

## 10. 完成度・安定性

評価軸は「バス係数 / リリース頻度 / 破壊的変更の頻度 / 既知バグ」。スター数ランキングにはしない。

| ライブラリ | 最新版（調査時点） | 開発体制 | 破壊的変更 | ドキュメント | TS 型 | ライセンス上の注意 |
|---|---|---|---|---|---|---|
| **Plotly.js** | 3.7.0 | 企業 + OSS | 安定 | 最上級 | 同梱 | MIT |
| **ECharts** | 5.x | **Apache 財団 + 企業。バス係数最高** | 安定 | 最上級・日本語情報も多い | 同梱 | Apache-2.0 |
| **Chart.js** | 4.5.1 | コミュニティ複数メンテナ。バス係数高 | v4 で安定 | 充実 | 同梱 | MIT |
| **webgl-plot** | — | **個人。チャート機能は未成熟** | — | 薄い | あり | MIT |
| （参考）**uPlot** | 1.6.32 (2026-03) | **個人単独。バス係数 1** | 1.6 系で長期安定 | デモ豊富・解説は薄い | 同梱 | MIT |

緩和材料になる（ただし本アプリでは足切りで失格）。

## 11. 実機確認手順（未実施）

代替ライブラリの性能に関する記述は**すべて公表値からの推定であり、未実測**である。
また v3.1 の最適化（§3.6）も**実機での効果測定は未実施**。以下を推奨する。

### 11-1. v3.1 の効果確認（最優先）

1. **コンテキストリークが実在したかの確認**:
   `releaseWebglContext` の呼び出しを一時的にコメントアウトし、
   保存を開始して再間引きを何度も起こす。コンソールに
   `Too many active WebGL contexts. Oldest context will be lost.` が出れば
   リークは実在した（= v3.1 の修正が有効）。出なければ plotly 3.7.0 で既に修正済み。
2. **`hoverinfo: 'skip'` の効果**: 一時的に外して DevTools Performance で
   再描画 1 回あたりの時間を比較する。2048 点 × 4 チャートで有意差が出るはず。
3. **2048 点で 200ms 予算に収まるか**をモード A / モード B の両方で確認。

### 11-2. 点数をさらに上げる場合

1. **基準線の取得**: `CHART_MAX_POINTS` を 8192 / 32768 に変更し、
   **現行 Plotly のまま** Chrome DevTools Performance でフレームタイムを計測する。
2. **モード B（ひずみ-応力ループ）で必ず計測すること。**
   時系列だけで判断すると間引きが効きすぎて実負荷を過小評価する（§4-2）。
3. **対象実機**: Android 実機、Windows、Linux、可能なら iOS Safari / macOS。
4. **指標**:
   - フレームタイム（目標: 200ms = 5fps の再描画予算に収まるか）
   - **ポーリング周期のジッタ** — 描画が主スレッドを塞ぐと計測周期が乱れる（§4-4）
   - `chrome://gpu` のハードウェアアクセラレーション状態
   - WebGL コンテキストロストの発生有無（4 チャート同時、特に iOS）
   - 長時間セッションのメモリ推移
5. **判断**: 現行 Plotly が目標点数で予算内に収まるなら、
   移行の動機はバンドルサイズのみになる。収まらないなら二段構えの検討へ進む。
